# mihi — P(-1) audit / hardening sweep (2026-08-23)

**Cuts**: pre-1.2.3 (audited surface = 1.2.2 code, cyrius 6.5.35 stdlib,
ai-hwaccel 2.3.18 transitive).
**Auditor**: mihi maintainer + Claude pair-review session.
**Outcome**: 1.2.3 lands **six code fixes** (A-1 … A-5, D-3), **four
documentation corrections** (D-1 … D-4), one new ADR, and 21 new
regression assertions. Two findings are documented rather than fixed
(A-6, A-7). No critical vulnerabilities; A-3 and A-4 are the two that
could reach a consumer as something other than a wrong number.

This is the second full audit. The first
([2026-05-19](2026-05-19-audit.md)) covered 0.5.0 and produced C-1 /
M-1 / C-2. Two of this sweep's findings are **direct descendants of
that one** — A-2 and A-3 are places where the 0.6.0 fixes bounded one
step of an arithmetic chain and left the next step unbounded. That is
the single most useful thing this audit says about the last one:
capping an accumulator is not the same as making the value it feeds
safe.

## Scope

| Layer | Surface |
|---|---|
| Direct syscalls | `uname(2)`, `sysinfo(2)` (both via `lib/sys.cyr`), `open(2)` + `read(2)` + `close(2)` of `/proc/cpuinfo`, `/proc/meminfo`, `/proc/uptime`, `/etc/os-release`, `/sys/devices/system/cpu/online`; `cpuid` leaves 0x80000002/3/4 |
| Direct parsers | `mihi_parse_cpu_range`, `mihi_parse_cpu_model`, `mihi_cpu_model_cpuid`, `mihi_cpu_brand_fill`, `mihi_find_meminfo_field`, `mihi_parse_meminfo_kb`, `mihi_extract_meminfo_bytes`, `mihi_parse_uptime_secs`, `mihi_find_osrelease_key`, `mihi_parse_osrelease_value` |
| Shared I/O (new) | `_mihi_read_probe_file` — see [ADR 0003](../adr/0003-shared-probe-read.md) |
| Transitive (ai-hwaccel 2.3.18 under the no-exec mask) | `/sys/class/drm/cardN/device/{vendor,device,product_name,mem_info_vram_total,mem_info_vram_used,driver,hwmon/*,gpu_busy_percent}`, `/sys/class/accel/*`, `/sys/class/misc/{intel_npu,samsung_npu,mtk_apu,qaic}/`, `/dev/{groq,neuron*}`, PCIe + NUMA sysfs trees, `readlink(2)` |
| Out of scope | ai-hwaccel's own source (audited upstream), cyrius stdlib internals, the AGNOS kernel ABI |

## Methodology

Two passes, per the `feedback-security-audit-web-research` memory: a
clean audit is *not* possible from internal review alone.

1. **Internal review** — per-file walk of `src/*.cyr`, checking bounds
   on every `load8`/`store8`, syscall return handling, integer overflow
   across *whole arithmetic chains* rather than per-expression, buffer
   mutation limits, file-descriptor lifetime, and the AGNOS/Linux
   `#ifdef` split for constants that exist on only one target.
2. **External research** — kernel and freedesktop source-of-truth docs
   re-read for every probe (`proc_meminfo(5)`, `os-release(5)`,
   `Documentation/admin-guide/cputopology.rst`,
   `arch/arm64/kernel/cpuinfo.c`), then CVE/NVD/MITRE searched for the
   syscalls and `/proc` + `/sys` paths mihi and ai-hwaccel touch.

Pass 2 changed the outcome twice this time: D-1 and D-2 are both cases
where mihi's own comment asserted something about the kernel or the
spec that turned out to be false, and neither is findable by reading
mihi's source.

## Findings — internal

### A-1 — silent truncation, short reads, and `-EINTR` in six hand-rolled read sites (medium)

**Files**: `src/cpu.cyr`, `src/mem.cyr`, `src/host.cyr` (six copies)
**Class**: Input validation / incorrect result
**Description**: Every file-reading probe did `open / one read / close`
and tested only `n <= 0`. Three consequences:

- A read that returned exactly `cap` was indistinguishable from EOF, so
  an undersized buffer produced a **plausible wrong value, not an
  error**. `mihi_uptime_secs(&buf, 4)` against a 20-byte `/proc/uptime`
  returned the first four digits as a whole uptime. `MemTotal:
  61192260 kB` cut after `611` parses as 611 kB.
- `read(2)` is permitted to return a short count; the code treated any
  short return as EOF. **This one was not theoretical — it was
  happening on every call.** Measured on the test host: a single
  `read(fd, buf, 8192)` on `/proc/cpuinfo` returns **3288 bytes**, two
  CPU blocks' worth, and it takes **three** reads to fill 8192. So
  `mihi_cpu_model` had been parsing 3288 bytes of the 8192 its caller
  supplied, on every invocation, since 0.2.0. It found `model name`
  anyway because that field is ~1.6 kB in — the defect was masked by
  the field's position, not absent. (`/proc/meminfo`, `/proc/uptime`
  and `/etc/os-release` each returned whole in one read, at 1671 / 20 /
  382 bytes, so those three were unaffected in practice.)
- `-EINTR` was reported as "fact not available" rather than retried.

**Exposure**: No memory-safety consequence — every parser stays inside
`len`. The harm is a wrong fact presented with the same confidence as a
right one, from a library whose entire product is facts. Reachable
without an attacker: any consumer passing a buffer smaller than the
file hits it, which is why `/proc/cpuinfo` (26 kB on the 16-thread test
host, against a documented 8 kB recommendation) had been silently
truncating since 0.2.0.
**Fix landed in 1.2.3**: new `src/io.cyr` /
`_mihi_read_probe_file(path, buf, cap, mode)`. Loops the read, retries
`-EINTR` up to 8 times, and detects truncation with one extra
single-byte read when the buffer fills. `mode` distinguishes the five
sites where truncation is fatal from `/proc/cpuinfo`, where a prefix is
what the probe actually wants. Rationale and the rejected alternatives
are in [ADR 0003](../adr/0003-shared-probe-read.md).
**Also folded in**: `O_NONBLOCK` and `O_CLOEXEC` on the open — see the
"symlink and FIFO" note under External below.

### A-2 — `mihi_parse_cpu_range` accumulates `total` without a bound (low)

**File**: `src/cpu.cyr`, `mihi_parse_cpu_range`
**Class**: Integer overflow on adversarial input
**Description**: The 0.6.0 C-2 fix capped each range bound at 18
digits, which bounds every *addend* below 10^18 — but the running
`total` was never bounded. Ten such ranges sum past i64 max and the
returned CPU count wraps negative.
**Exposure**: Theoretical, and it was *arithmetically unreachable*
before this cut: the 64-byte read buffer could not hold enough 19-byte
ranges to overflow. A-1's fix raised that buffer to 1024 bytes, which
is precisely when a latent bound becomes a live one — worth recording,
because the fix for one finding created the reachability for another.
**Fix landed in 1.2.3**: check `total > MIHI_CPU_MAX` (2^20, two orders
of magnitude past Linux's 8192-CPU `CONFIG_NR_CPUS` ceiling) each
iteration and report malformed input the way the function already does
elsewhere — return 0.

### A-3 — `kB → bytes` scale overflows to a NEGATIVE byte count (medium)

**File**: `src/mem.cyr`, `mihi_extract_meminfo_bytes`
**Class**: Integer overflow → invalid result crossing an API boundary
**Description**: 0.6.0's M-1 capped `mihi_parse_meminfo_kb`'s
accumulator at 18 digits. `mihi_extract_meminfo_bytes` then returns
`kb * 1024`. 10^18 × 1024 is ~1.02e21 — about four times i64 max — so
the guard that made the *accumulator* safe left the *scale* able to
wrap. Measured: `MemTotal: 999999999999999999 kB` returned
**-9017668127734891520**.
**Exposure**: The value is negative, which is the same sentinel space
`mihi_mem_total` uses for failure (`0 - 1`), so a consumer doing the
documented `if (total < 0) { /* unavailable */ }` degrades correctly —
but one doing `if (total == 0 - 1)` renders a nonsense figure, and one
doing unsigned arithmetic on it gets 9.4 exabytes. Requires write
access to `/proc/meminfo`, which means root, which means the box is
already lost — the same threat model as 0.6.0's M-1, and the same
reason to fix it anyway.
**Fix landed in 1.2.3**: reject rather than saturate. `kb >
MIHI_MEM_KB_MAX` (2^53 - 1 = floor(i64max / 1024), about 9 EiB of RAM)
returns `0 - 1`. A value that large is not a truncated fact, it is a
corrupt one.

### A-4 — `mihi_uname` left the caller's buffer uninitialised on failure (medium)

**File**: `src/kernel.cyr`, `mihi_uname`
**Class**: Out-of-bounds read reachable from a caller mistake
**Description**: `mihi_uname` passed the caller's stack buffer straight
to `sys_uname` and wrapped the result in a `Result`. On failure the
buffer was left exactly as the caller allocated it — uninitialised
stack. The four field accessors (`mihi_kernel_name`,
`mihi_kernel_version`, `mihi_cpu_arch`, `mihi_hostname`) are pure
pointer arithmetic and, by the ADR 0001 contract, deliberately do not
check that the fill succeeded. So a caller that ignores the `Result` —
which the contract permits them to get wrong, and which is the easiest
mistake to make against this API — received a "cstring" pointing into
uninitialised stack **with no NUL anywhere in it**, and the consumer's
`println()` walked off the end of the buffer.
**Exposure**: This is the only place in mihi where a caller mistake
turned into an out-of-bounds read rather than a wrong value. It needs
`uname(2)` to fail, which on Linux essentially means `-EFAULT` — so it
is not attacker-reachable on a healthy host. It *is* reachable on a
target where the syscall is unwired: `lib/sys.cyr` returns `-ENOSYS`
for Windows, and did for macOS before cyrius 6.5.16. A consumer built
for such a target and ignoring the Result reads out of bounds every
time.
**Fix landed in 1.2.3**: zero `UTS_SIZE` bytes before the syscall. Cost
is one pass over 390 bytes (64 on AGNOS), once. The worst case becomes
an empty string — which the existing "zero-init uts" test already
asserts is safe. `lib/sys.cyr`'s macOS arm zeroes for exactly this
reason; mihi's wrapper had not adopted it.

### A-5 — `mihi_mem_free` had no AGNOS arm and a stale justification (low)

**File**: `src/mem.cyr`, `mihi_mem_free`
**Class**: Portability gap / stale documentation
**Description**: Alone among the file-reading probes, `mihi_mem_free`
carried no `#ifdef CYRIUS_TARGET_AGNOS` branch. On the sovereign target
it fell through to a Linux `open("/proc/meminfo")` that cannot succeed,
so it returned `0 - 1` permanently. The 1.1.2 CHANGELOG justified this
as "no sysinfo equivalent" — true when written, false since
`lib/sys.cyr` grew the AGNOS §4.4 layout, which publishes `freeram` at
`SI_FREERAM` (+16) and reads it through the per-target
`sysinfo_free_memory()`.

A second, subtler problem: because the function had no AGNOS guard, its
`O_RDONLY` was compiled on the AGNOS target, where it resolves from
`lib/io.cyr`'s agnos-only `O_*` set rather than the Linux syscall enum.
Harmless at value 0, but it meant A-1's `O_NONBLOCK | O_CLOEXEC`
hardening could not have been applied there — those two are **not
defined** on AGNOS, so the shared helper's body has to be
`#ifndef CYRIUS_TARGET_AGNOS`.
**Fix landed in 1.2.3**: real AGNOS arm reading `sysinfo_free_memory()`.
The semantic difference is documented at the call site and not papered
over: Linux reports `MemAvailable` (free + reclaimable), AGNOS §4.4
reports plain free. Separate code path, not a fallback chain — per
CLAUDE.md.

### A-6 — the 1.2.2 log-level clamp widens ADR 0002's first-call race (informational)

**File**: `src/gpu.cyr`, `_mihi_gpu_ensure`
**Class**: Concurrency, pre-existing class
**Description**: 1.2.2 made `_mihi_gpu_ensure` save the caller's
`sakshi` log level, clamp it to `SK_WARN` across
`registry_detect_no_exec()`, and restore it. ADR 0002 already documents
that the first-call singleton init has a TOCTOU window under a
multi-threaded consumer. The clamp adds a second thing to that window:
with two threads interleaved as *A saves INFO → A clamps → B saves WARN
→ A restores INFO → B restores WARN*, the process is left at `SK_WARN`
permanently.
**Exposure**: None today — every mihi consumer (`iam`, `chakshu`, the
smoke binary) is single-threaded at the point of first GPU probe, which
is the same precondition ADR 0002 already relies on. Recording it
because it is a consequence of a change made in the *previous* cut and
would otherwise be invisible.
**Fix**: None. Adding a lock would put a threading dependency inside a
probe, against the "no allocator/thread dependency from probe
internals" rule. ADR 0002's alternative-3 (an explicit
`mihi_gpu_init()` entry point) remains the forward path and now has a
second reason to exist; ADR 0002's Consequences section has been
amended to say so.

### A-7 — `mihi_cpu_brand_fill` writes 48 bytes with no capacity parameter (informational)

**File**: `src/cpu.cyr`, `mihi_cpu_brand_fill`
**Class**: Trust boundary / API shape
**Description**: The function takes only `buf` and unconditionally
stores 48 bytes of CPUID brand string through it. Its capacity contract
lives in a comment ("`buf` MUST be >= 48 bytes") and is enforced only
by its one in-tree caller, `mihi_cpu_model_cpuid`, which checks
`cap < 49`. It carries no leading underscore, so it is part of the
bundle's public surface and a consumer can call it directly with a
short buffer.
**Exposure**: No in-tree misuse. Not attacker-controlled — the 48 bytes
come from the `cpuid` instruction, not from any file.
**Fix**: None possible without a signature change, and the API has been
frozen since 1.0.0; adding a `cap` parameter is a v2.0 item. Recorded
here and in `docs/sources.md` so the next consumer integration has it
in writing. The comment has been strengthened at the definition.

## Findings — documentation

CLAUDE.md requires a source citation on every probe. Four were wrong or
misleading. These matter more than usual for this library: the citation
*is* the contract a consumer reasons about.

### D-1 — `mihi_cpu_model` cited an aarch64 source the kernel does not emit

The comment claimed the `model name` field comes from "CPUID
brand-string leaves (x86) or device-tree `/cpus/cpu@N/compatible`
(aarch64)". arm64's `c_show()` (`arch/arm64/kernel/cpuinfo.c`) prints
`processor`, `BogoMIPS`, `Features`, `CPU implementer`, `CPU
architecture`, `CPU variant`, `CPU part`, `CPU revision` — and **no
`model name` line at all**. So on aarch64 Linux this probe returns 0,
always, and the citation implied otherwise. cyrius supports
`--aarch64`, so this is a reachable target, not a hypothetical.
**Corrected in 1.2.3**; sourcing an arm64 brand from the device tree is
a second source for one fact and needs hardware to verify, so it is
filed in `roadmap.md` rather than guessed at here.

### D-2 — the `mihi_distro` fallback rested on a false claim about os-release(5)

Both the module header and the probe comment justified the
`PRETTY_NAME` → `ID` fallback on the grounds that the spec makes
`PRETTY_NAME` optional and `ID` "the mandatory minimum every distro
must ship". os-release(5) makes **both** optional: *"If not set, a
default of `ID=linux` may be used"*, and likewise
`PRETTY_NAME="Linux"`. The fallback is still the right behaviour, but
it rests on the weaker true reason — those two keys are the only ones
that name the OS — and a file with neither yields null rather than a
guess. **Corrected in 1.2.3.**

### D-3 — single-quoted os-release values were not handled (also a code fix)

os-release(5): *"Variable assignment values must be enclosed in double
or single quotes if they include spaces, semicolons or other special
characters."* `mihi_parse_osrelease_value` tested only `"` (0x22). A
distro shipping `PRETTY_NAME='Some Linux'` fell through to the bare
branch, which scans to the newline — so the probe returned the value
**with its quotes still attached**. Every mainstream distro uses double
quotes, which is why it survived two audits.
**Fixed in 1.2.3** with a symmetric single/double delimiter match, plus
a test that an apostrophe inside a double-quoted value stays literal.
Backslash escaping remains deliberately unimplemented and is now
documented as a known limit in `docs/sources.md` rather than silently
absent.

### D-4 — "recommend 8192" read as "the file fits"

`mihi_cpu_model`'s buffer recommendation was written as though 8 kB
held `/proc/cpuinfo`. That file is one block per logical CPU: **26,322
bytes** on the 16-thread test host, and it grows with core count. The
recommendation is really "CPU 0's block fits", which is all the probe
wants. Left implicit, it turned into a bug during this very sweep — the
first cut of A-1's fix treated truncation as fatal everywhere and broke
`mihi_cpu_model` on any machine with more than about five cores.
**Corrected in 1.2.3**, and the distinction is now load-bearing in the
code as `MIHI_IO_PREFIX` vs `MIHI_IO_WHOLE`.

## Findings — external (CVE / kernel + spec docs)

### Class precedent for A-2 and A-3 — consumer-side procfs integer overflows

Neither A-2 nor A-3 is a CVE in mihi. Both are in a class with a real
CVE history on the *consumer* side of `/proc`, which is what justifies
fixing them despite the root-only threat model:

- **[CVE-2018-1124](https://nvd.nist.gov/vuln/detail/CVE-2018-1124)** —
  procps-ng `file2strvec()`: multiple integer overflows parsing procfs
  content led to heap corruption and local privilege escalation. Same
  shape as A-3: the bug is in the *reader*, and the attacker's leverage
  is what they can get written into `/proc`.
- **[CVE-2021-37600](https://nvd.nist.gov/vuln/detail/CVE-2021-37600)**
  — util-linux: integer overflow reading `/proc/sysvipc/sem`, with
  potential buffer overflow behind it.

mihi's parsers write into caller-supplied fixed buffers and are
`len`-bounded throughout, so neither overflow can reach memory here —
the damage stops at a wrong number. That is the difference between
these findings and those CVEs, and it is a property of the ADR 0001
buffer convention rather than luck.

### Class precedent for the `O_NONBLOCK` hardening — repointed symlinks

os-release(5) states `/etc/os-release` *"should be a relative symlink to
`/usr/lib/os-release`"*. mihi therefore cannot use `O_NOFOLLOW`: the
symlink is legitimate. The residual risk is a symlink repointed at a
FIFO, where a blocking `open(2)` hangs the caller — and mihi's first
consumer renders the **login MOTD**, so a hang there is a login denial
rather than a slow command. Symlink-substitution against
system-managed paths has repeated precedent
([CVE-2018-6954](https://nvd.nist.gov/vuln/detail/CVE-2018-6954),
systemd-tmpfiles; and the 2026 Himmelblau symlink privesc
[CVE-2026-31979](https://nvd.nist.gov/vuln/detail/CVE-2026-31979)) —
neither affects mihi, both describe the manoeuvre. `O_NONBLOCK` makes
the FIFO case an immediate `-EAGAIN`, which becomes an honest probe
error. Writing `/etc` still requires root; this is defence in depth,
not a patched vulnerability.

### Kernel-side procfs CVEs reviewed — not on mihi's path

- **[CVE-2024-53107](https://nvd.nist.gov/vuln/detail/CVE-2024-53107)**
  — integer overflow in `pagemap_scan_get_args()`, `fs/proc/task_mmu`.
  mihi reads no per-process procfs.
- **CVE-2007-6694** — `/proc/cpuinfo` DoS on some PowerPC machines.
  Kernel-side, ppc-only, long fixed; noted because it is the only
  `/proc/cpuinfo` read-path CVE found in any year.
- **[CVE-2025-38653](https://osv.dev/vulnerability/CVE-2025-38653)** —
  use-after-free via `proc_ops->proc_lseek` on module unload. mihi
  never seeks; it opens, reads, closes.

### Transitive — ai-hwaccel 2.3.18 → amdgpu sysfs

Carried forward from the 2026-05-19 audit, both still the directly
relevant ones because mihi reads these attributes through
`registry_detect_no_exec()`:

- **[CVE-2025-40289](https://nvd.nist.gov/vuln/detail/CVE-2025-40289)**
  — VRAM sysfs attributes exposed on AMD GPUs that have no VRAM; reading
  them can crash. This is `mem_info_vram_total`, i.e. exactly mihi's
  transitive read path. Unchanged assessment: kernel-side, no mihi
  avoidance path, and ai-hwaccel's `detect_rocm` already degrades when
  the read fails.
- **[CVE-2025-40288](https://nvd.nist.gov/vuln/detail/CVE-2025-40288)**
  — `ttm_resource_manager_usage()` NULL deref on APUs.

New in this audit window (2026), all reviewed, none on mihi's read
path:

- **CVE-2026-63879** — amdgpu GPU-memory-management race, CVSS 7.8,
  local. Affects 6.2 through 7.0.11, fixed in 7.0.12 and 7.1. The test
  host runs **7.1.8-arch1-3** and is past the fix. Consumers on an
  older kernel should patch; this is the highest-severity item in the
  transitive set.
- **CVE-2026-46229** — AMD KFD does not clear VRAM on allocation,
  leaking prior workload contents. Allocation path; mihi allocates no
  GPU memory and reads only sysfs attributes.
- **CVE-2026-53293** — deadlock in `AMDGPU_INFO_READ_MMR_REG`. An
  ioctl; mihi's transitive surface is sysfs reads plus `readlink(2)`,
  and the no-exec mask does not enable an ioctl path.
- **CVE-2026-43318** — DMA-BUF sync bug causing GPU page faults. Not
  reached.

### Spec / kernel documentation confirmed

- `proc_meminfo(5)`: values are labelled `kB` but are really **KiB**
  (1024 B); the label is left wrong deliberately because programs parse
  it. mihi's `* 1024` is correct, and this is now stated at the call
  site so nobody "fixes" it to 1000.
- `MemAvailable` is Linux 3.14+ (`%lu`). On an older kernel the field is
  absent and `mihi_mem_free` returns `0 - 1` — now documented.
- `Documentation/admin-guide/cputopology.rst`: `/sys/devices/system/cpu/online`
  is a `%*pbl` range list, which is why a machine with many offline CPUs
  can produce a long comma-separated value — the basis for A-1's buffer
  increase.
- `os-release(5)`: quoting rules (D-3), optionality of `ID` and
  `PRETTY_NAME` (D-2), and the expected symlink (`O_NONBLOCK` note).
- `arch/arm64/kernel/cpuinfo.c`: no `model name` field (D-1).

## Performance (P(-1) step 2)

Baseline captured with `./scripts/bench-history.sh` on archaemenid
(Ryzen 7 5800H, kernel 7.1.8-arch1-3, cyrius 6.5.35), and — because
this sweep changed the read path under every probe — re-measured
against the **1.2.2 source built in a scratch worktree on the same
host, kernel and toolchain**, so the comparison is the code and
nothing else.

| Probe | 1.2.2 | 1.2.3 | Δ |
|---|---:|---:|---:|
| `mihi_uname` | 481 ns | 1.014 µs | +533 ns |
| `mihi_cpu_count` | 5.21 µs | 5.79 µs | +11% |
| `mihi_mem_total` | 8.95 µs | 9.54 µs | +7% |
| `mihi_mem_free` | 9.55 µs | 9.80 µs | +3% |
| `mihi_uptime_secs` | 21.64 µs | 22.22 µs | +3% |
| `mihi_distro` | 3.44 µs | 3.99 µs | +16% |
| `mihi_cpu_model` | 37.34 µs | **84.51 µs** | **+126%** |

Pure parsers and field accessors are unchanged (25–411 ns and 2–3 ns
respectively).

Two of these are worth explaining rather than waving through.

**`mihi_uname` +533 ns** is A-4's zeroing: 390 byte-stores before the
syscall, once. That is the whole cost of turning a potential
out-of-bounds read into an empty string, and it is paid once per
process because the uts buffer is filled once and shared across four
probes (ADR 0001).

**`mihi_cpu_model` +126%** is the honest price of A-1, and it is the
same measurement as the short-read finding above. 1.2.2 issued one
`read()` and got 3288 bytes; 1.2.3 loops and gets the 8192 the caller
asked for, which means three reads and ~2.5× as much seq_file
generation kernel-side. The probe is not slower at doing the same work
— it is now doing the work it always claimed to.

Considered and rejected: making `MIHI_IO_PREFIX` stop after the first
successful read, which would restore 37 µs exactly. It also restores
the defect. `/proc/cpuinfo`'s first read happens to contain `model
name` on x86, but that is a property of where the kernel puts the field
and how big a CPU block is, not a guarantee — and a probe that works
because of where a field happens to land is the kind of thing this
audit exists to remove. The probe is called once per process on the
login path; 47 µs there is not a cost worth buying the fragility back
with.

The remaining +3–16% is the shared helper's call overhead plus the two
extra open flags, on probes whose files already fit in one read.

## Deferred / out of scope

- **arm64 CPU-brand source** (from D-1). Reading
  `/proc/device-tree/model` or `/sys/firmware/devicetree/base/model`
  would give aarch64 Linux a model string, but it is a second source
  for one fact and cannot be verified without arm64 hardware. Filed in
  `roadmap.md`.
- **`mihi_cpu_brand_fill(buf, cap)`** (A-7). Signature change; v2.0.
- **Backslash unescaping in os-release values** (D-3 tail). Requires
  rewriting a value in place and shorter; no observed distro escapes
  inside `PRETTY_NAME` or `ID`. Documented as a limit in
  `docs/sources.md`.
- **Locking for the gpu singleton** (A-6). Blocked on the "no thread
  dependency from probe internals" rule; ADR 0002 alternative-3 is the
  path when a multi-threaded consumer appears.

## Methodology note for future audits

The 0.6.0 audit's own fixes generated two of this audit's findings.
C-2 capped the digits feeding `mihi_parse_cpu_range`'s addends but not
the total they accumulate into (A-2); M-1 capped the digits feeding
`mihi_parse_meminfo_kb` but not the `× 1024` that consumes its result
(A-3). Both were *correct* fixes to the expressions they were pointed
at. The lesson for the next sweep is to audit the **arithmetic chain
end to end** — from the byte in the file to the value crossing the API
boundary — rather than the expression where the previous finding
happened to land.

The second lesson is the older one, and it held again: external
research is not optional. D-1 and D-2 are both mihi asserting something
false about a kernel or a spec, and no amount of reading mihi's source
would have surfaced either.
