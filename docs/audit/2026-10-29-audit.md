# mihi — P(-1) audit / hardening sweep (2026-10-29)

**Cut**: 1.3.2. The audited surface is the 1.3.1 code (`cdcd15b`): cyrius
6.7.18 stdlib, ai-hwaccel 2.5.5 transitive, bayan 1.11.1 (dev only).
**Auditor**: mihi maintainer and a Claude session. The session ran its own
internal review and, in parallel, an independent review agent briefed with
the code and the methodology but not the session's conclusions. It also ran
an external-research pass against NVD / MITRE and primary sources.
**Outcome**: 1.3.2 lands **fourteen code fixes** (B-1 … B-14), **eight
documentation and tooling corrections** (E-1 … E-8), two shared scanners
replacing seven hand-rolled loops, a real fuzz harness, three CI gates, and
**71 new assertions (143 → 214)**. Three upstream or residual findings are
documented rather than fixed (U-1 … U-3), and nine accepted limits are
recorded (L-1 … L-9). There are no critical findings. B-10 and B-11 are the
two that could have done something other than return a wrong number: an
out-of-bounds read, and a change to process state.

This is the third full audit, after [2026-05-19](2026-05-19-audit.md) (0.6.0)
and [2026-08-23](2026-08-23-audit.md) (1.2.3). Since the second one the
toolchain has moved 6.5.35 → 6.7.18 and ai-hwaccel 2.3.18 → 2.5.5, and the
no-exec surface mihi reaches through ai-hwaccel has grown from 8 backends to
16.

The headline repeats the last audit's lesson, one level down. Its
methodology note said to audit every arithmetic chain from the byte in the
file to the value at the API. B-2 is the same defect in three parsers. Each
capped its digit accumulator at 18 digits, which keeps the accumulator from
wrapping, and then returned the first 18 digits of a longer number as the
value. The two regression tests the 0.6.0 audit wrote for those caps
asserted the truncated value. Bounding a loop is not the same as rejecting
its input.

## Methodology

1. **Baseline** on the current pins before any change: build, lint, fmt,
   143/143 tests, and a benchmark run (`cdcd15b` rows in
   `docs/benchmarks/history.csv`). The previous rows were from `188a7d3`
   (1.2.3, cyrius 6.5.35).
2. **Internal review** of every module, reading each parser's chain end to
   end, plus `cyrius coverage` (26 / 27 functions referenced; the one
   unreferenced, `mihi_cpu_brand_fill`, is exercised through
   `mihi_cpu_model_cpuid`).
3. **Independent review** by a separate agent given the code, the rules and
   the methodology note, but none of the internal findings. It confirmed
   B-1, B-2, B-3, B-4, B-8, B-9 and B-10 by running them, and found B-11,
   B-12, B-13 and B-14, which the internal pass had missed.
4. **External research**: NVD / MITRE searches for 2026-08-23 → 2026-10-29
   and all-time on every source in the scope table, plus primary-source
   checks (kernel 7.3 source, man-pages 6.19, os-release(5) at systemd 262,
   the Devicetree spec). The search list is under *Findings — external*.
5. **Repairs**, each with a regression test that names the 1.3.1 result.
   Then a **mutation check**: each fix was undone in a scratch copy and the
   suite was required to go red. All did except B-8's integration, which
   cannot fail on a CPU that has the brand leaves; its pure check is tested.
6. **Fuzzing**: `tests/mihi.fcyr`, 180,000 invariant checks per run, plain,
   `--bounds` and `--poison`. It was mutation-checked too: an out-of-bounds
   write planted in `_mihi_osrelease_pick` was caught within 14 checks, a
   disabled seal within 8.
7. **Re-measurement** of everything on the final tree.

## Findings — code

### B-1 — the truncation read's errors counted as "end of file" (medium, wrong value)

`_mihi_read_probe_file` decides whether a buffer that filled exactly was the
whole file by reading one more byte. Only `extra > 0` was tested. A `-EINTR`
or `-EIO` on that read therefore meant "nothing more", and a cut file came
back as a plausible value. That is the A-1 defect the module was written to
close, surviving on its last syscall. The independent review notes that
EINTR there is plausible under LXCFS, whose FUSE-backed `/proc/meminfo` and
`/proc/uptime` are interruptible. It also reproduced the shape with a FIFO
that holds 8 bytes and a writer: cap 8 came back as a whole file.
**Fix**: the extra read shares the `-EINTR` budget, and any other error is a
failure. The decision moved into a pure `_mihi_io_verdict(total, extra)` so
the tests can drive the error cases.

### B-2 — the 18-digit caps returned truncated numbers (medium, wrong value)

`mihi_parse_uptime_secs`, `mihi_parse_meminfo_kb` and both bounds in
`mihi_parse_cpu_range` stopped accumulating at 18 digits and returned what
they had. Observed on 1.3.1:

- a 20-digit uptime gave `123456789012345678`;
- `0000000000000000001234.56` gave 0;
- `MemTotal: 0000000000000008000000 kB` gave 819,200 bytes (800 kB, not 8 GB);
- `cpu_range("1234567890123456789")` gave **2**, because the 19th digit was
  parsed as a second range.

The meminfo path was partly saved by A-3's `MIHI_MEM_KB_MAX` check;
uptime's was not saved at all. The M-1 and C-2 regression tests from 0.6.0
asserted the truncated values. **Fix**: one digit reader,
`_mihi_parse_uint`, returns `OVERLONG` when a 19th digit follows. Every
parser uses it. The two old tests flipped to assert the error.

### B-3 — `mihi_parse_cpu_range` returned partial counts on malformed input (low, wrong value)

A byte that was neither digit nor separator stopped the loop and returned
the count so far: `"0-3,x"` gave 4, and so did `"0-3x"`. `"5-"` counted 1.
A tab is not a separator in the kernel's format, so `"0-7\t8-15"` gave 8.
The kernel prints `%*pbl` + `\n`: decimal, `-`, `,` and `\n` only
(`bitmap_list_string`, lib/vsprintf.c). **Fix**: malformed anywhere is 0,
the function's existing error value, as A-2 already used for overflow. The
C-1 coercion of descending ranges stays.

### B-4 — an empty `model name` value came back as `""` (low)

`"model name\t: \n"` returned a non-null empty string. The CPUID and
os-release paths return null for blank values. **Fix**: null.

### B-5 — a quoted os-release value ran across lines (medium, wrong value; attacker-influenced input)

The closing-quote scan did not stop at a newline. `PRETTY_NAME="Foo` with no
closing quote, followed by `NAME="Bar"`, came back as the multi-line value
`Foo\nNAME=`. `/etc/os-release` is the one input mihi reads that a package
or a container image writes, and the value goes to a login banner.
**Fix**: a quoted value ends at its line, and an open quote is malformed.

### B-6 — a bare os-release value on an unterminated last line was null (low)

os-release(5) does not require a trailing newline, and the parser's comment
said a bare value ends at "the trailing '\n' (or EOF)". The code returned
null at EOF: it cannot write a NUL past `len`. So a file ending `ID=arch`
with no newline and no PRETTY_NAME gave no distro. **Fix**: `mihi_distro`
reads into `cap - 1` and gives an unterminated last line its newline. The
file must now fit in `cap - 1` (recommended `cap` is 1024; files are around
500 bytes). The post-read logic is now the pure `_mihi_osrelease_pick`.

### B-7 — the ID fallback skipped a PRETTY_NAME that was present but unusable (low)

`PRETTY_NAME=""` or an open-quoted PRETTY_NAME returned null instead of
falling back to `ID`. **Fix**: the one documented fallback now covers an
unusable value as well as an absent one. A failed parse writes nothing, so
`ID` is read from the same, unmodified buffer.

### B-8 — the CPUID brand leaves were read without checking they exist (medium on AGNOS, wrong value)

`mihi_cpu_model_cpuid` (the AGNOS path) read leaves 0x80000002–4 without
checking `CPUID.80000000H:EAX`. Intel's SDM (Vol. 2A, CPUID) has an
out-of-range leaf return the highest *basic* leaf's registers. So on a CPU
or hypervisor that caps extended leaves below 0x80000004, the "brand" was 48
bytes of unrelated register data. Linux's `get_model_name`
(arch/x86/kernel/cpu/common.c) makes this exact check before it reads the
brand. **Fix**: `_mihi_cpuid_max_ext` plus `_mihi_cpuid_brand_ok`, which
requires 0x80000004 ≤ max ≤ 0x8000FFFF.

### B-9 — AGNOS sysinfo values used without bounds; a CPU count of 0 reported as 1 (low)

CLAUDE.md: "Do not trust external data (`/proc` content, kernel boot-info)
without bounds and range validation".

- `mihi_cpu_count` on AGNOS turned a reported 0 into 1, a fact the kernel
  did not state, and had no upper bound.
- `mihi_mem_total`, `mihi_mem_free` and `mihi_uptime_secs` passed a u64 past
  i64 max through as a negative number other than the documented -1.

**Fix**: a count below 1 or above `MIHI_CPU_MAX` is -1, and a negative value
is -1. Compile-verified (`--agnos`); there was no AGNOS run this cut
(roadmap 1.4.x).

### B-10 — AGNOS uname slots carry no terminator when full (medium, latent out-of-bounds read)

`agnos-userland-abi.md` §4.3 defines each of the four 16-byte slots as
"NUL-padded to fill the slot (**not** NUL-terminated-and-variable)", and the
kernel's `sysinfo_put_str(dst, src, 16)` copies up to 16 bytes. The field
accessors return `uts + UTS_X` as a cstring. A 16-character value would run:

- `mihi_kernel_version` into the machine slot;
- `mihi_cpu_arch` (the last slot) past the 64-byte buffer that ADR 0001
  tells the caller to allocate.

The A-4 comment's "the worst case is an empty string" did not hold on AGNOS.
Latent: the longest value today is `"aarch64"` (7). **Fix**:
`_mihi_uts_seal(uts, size, width)` zeroes any slot with no NUL. The field
then reads empty, A-4's honest "unknown", rather than cut to 15 characters.
It runs on AGNOS only: on Linux the NUL is guaranteed (uname(2);
`sethostname` refuses more than 64 bytes and zero-fills), and sealing there
cost ~320 ns a call for nothing.

### B-11 — the read path opened any file type, without `O_NOCTTY` (medium, change to process state)

Every path mihi reads is a regular file. procfs and sysfs attributes report
S_IFREG, and `/etc/os-release` is a symlink to one (all checked on the dev
host). The read path never checked that. Through the repointed-symlink case
the `O_NONBLOCK` flag answers:

- **a terminal**: opening a tty without `O_NOCTTY` makes it the controlling
  terminal of a session leader that has none. The independent review
  reproduced this: a forked child calls `setsid`, opens a pty pair, and runs
  the probe on `/dev/pts/N`; afterwards `/dev/tty` opens, and without the
  probe call it does not. Reading the tty would also consume what the user
  types.
- **any other device node**: some drivers act on open(2) itself. The kernel
  watchdog API documentation: the device "activates as soon as
  /dev/watchdog is opened".

**Fix**: `stat(2)` the path and open only a regular file; open with
`O_NOCTTY` (`0400`, asm-generic `fcntl.h`; not defined in the vendored
stdlib, so `MIHI_O_NOCTTY`); `fstat(2)` the descriptor and refuse a
non-regular file before any read. The second check closes the race for what
is *read*. **Residual (U-3)**: a device node swapped in between stat and
open is still opened. Closing that needs an `O_PATH` open plus a re-open
through `/proc/self/fd`, which would break the distro probe wherever `/proc`
is not mounted (chroots, minimal containers), for a path only root can
repoint. **Cost**: +1.0 to +2.6 µs per file probe (*Performance*).

### B-12 — the public parsers read before their buffer on a negative start (low, caller misuse)

`mihi_parse_meminfo_kb(buf, len, -1)` read the byte before `buf`; the
independent review put a `'7'` there and got 7 back.
`mihi_parse_osrelease_value(buf, len, -1)` returned `buf - 1`. -1 is what the
matching `find_*` returns for a missing key, and the test suite itself chains
the two unchecked. **Fix**: a negative start is the error value, in both and
in `_mihi_parse_uint`.

### B-13 — AGNOS `mihi_distro` returned a string literal, not a pointer into `buf` (low)

The contract is "a cstring into `buf`". A consumer editing the result in
place edited the literal, for every later call. **Fix**: copy `"AGNOS"` into
`buf` (`cap` ≥ 6).

### B-14 — `cpu.cyr` defined `CYRIUS_ARCH_X86` for every AGNOS build (low, latent)

1.2.1 needed the define: cyrius 6.2.x did not predefine it for `--agnos`.
On 6.7.18 a marker build shows `--agnos` defines `CYRIUS_ARCH_X86` and
`--aarch64` defines `CYRIUS_ARCH_AARCH64`, so the define was redundant. It
also leaked into every module after it, consumer code included. And it
claimed x86 for *any* AGNOS build, so a future aarch64 AGNOS target would
have assembled x86 CPUID bytes. The comment said such a target "would …
skip this"; it would not have. **Fix**: removed.

## Findings — upstream and residual

### U-1 — ai-hwaccel's no-exec PCIe pass can wake a runtime-suspended GPU (medium, side effect; not fixed here)

`registry_detect_no_exec()` runs `enrich_pcie`, which reads
`/sys/bus/pci/devices/<bdf>/max_link_{width,speed}` (and the bridges above)
for every profile with a PCI address. In kernel 7.3's `pci-sysfs.c` those
show functions call `pci_config_pm_runtime_get()`. That resumes a
runtime-suspended device, and a device in D3cold, for the config read. So on
a hybrid-graphics laptop, `mihi_gpu_count()` can wake a sleeping dGPU: power
and latency, not data. The "no subprocess" contract holds; this is a
different side effect, in ai-hwaccel's code. **Disposition**: roadmap 1.6.x,
file it upstream. A no-wake path (skip a device whose
`power/runtime_status` is `suspended`; that attribute does not resume it) is
the obvious ask.

### U-2 — distlib credits a named dep's leftover names to the bundle

Unchanged since 1.2.8 and still measured on 6.7.18. Roadmap 1.6.x.

### U-3 — residual windows in the read path

- the stat → open race in B-11, above;
- **LXCFS**: in containers, `/proc/cpuinfo`, `meminfo`, `uptime` and
  `/sys/devices/system/cpu/online` may be served by a FUSE daemon. Those are
  regular files, so `O_NONBLOCK` has no effect, and a hung daemon hangs the
  read. mihi cannot bound that without a thread or a timer, both outside the
  probe rules.

Both are recorded; neither has a fix that fits the probe rules.

**Spec and kernel facts confirmed** (they shaped B-3, B-5, B-6, B-8, B-10,
B-11 and the limits below):

- `cpu/online` is `sysfs_emit("%*pbl\n")`: ascending decimal, `-`, `,` only.
  The `a-b:c/d` stride form is parse-only. Output is capped at
  PAGE_SIZE − 1, silently, losing the `\n`. Such a file overruns mihi's
  1024-byte read and comes back as TRUNC, which is correct by construction.
- `/proc/meminfo` prints MemTotal, MemFree and MemAvailable
  unconditionally, in KiB, minimum width 8.
- `/proc/uptime` is `"%lu.%02lu %lu.%02lu\n"`. It is time-namespace
  adjusted, and an unprivileged user can set the offset through a user
  namespace. The result is bounded to about 4.6e9 s, inside the 18-digit
  rule.
- os-release(5) (systemd 262): quoted or bare values, backslash escapes, `#`
  comments, no line-length limit, PRETTY_NAME / ID optional. Non-printable
  characters "should not" be used, a *should*. **Use `/etc/os-release` when
  it exists, else `/usr/lib/os-release`** (L-4).
- Devicetree `compatible` is a NUL-separated string list. The kernel
  exports it raw and does not check the terminator; `mihi_parse_dt_string`
  already refuses an unterminated blob. On arm64 a cpu node's unit address
  is its MPIDR affinity, so `cpu@0` is conventional, not guaranteed (L-5).
- utsname: Linux fields are `char[65]`, NUL-terminated, but their bytes are
  not validated. A UTS-namespace root can set control characters (L-3).
- x86 `model name` prints `unknown` when the brand string is empty (L-6).
- seq_file returns whole records per read (short reads are normal), and
  `single_open` files arrive whole. kernfs bin attributes return at most
  PAGE_SIZE per read. `O_NONBLOCK` has no effect on regular files.

## Refactor

- **Shared scanners** in `io.cyr`: `_mihi_find_line_prefix` replaces three
  copies of the line-anchored search (meminfo, os-release, cpuinfo), and
  `_mihi_parse_uint` replaces four digit loops. Both are pure and tested.
  The public names (`mihi_find_meminfo_field`, `mihi_find_osrelease_key`,
  and the parsers) stay as thin wrappers, because the API is frozen. One
  public behaviour was kept on purpose: `mihi_parse_cpu_model` still refuses
  a match at offset 0 (real `/proc/cpuinfo` opens with `processor`; a test
  pins it).
- **Pure helpers** extracted for testability: `_mihi_io_verdict`,
  `_mihi_has_blank_line`, `_mihi_osrelease_pick`, `_mihi_cpuid_brand_ok`,
  `_mihi_uts_seal`, `_mihi_is_regular`.

## Methodology note for future audits

Two things this sweep found that the last one would have recommended
looking for, but did not:

1. **A test can pin a defect.** M-1 and C-2 were written to prove a cap
   "engaged", and they asserted the truncated value as correct. When a
   regression test asserts *how* a guard behaves, check that the behaviour
   it pins is the one the probe contract wants. A wrong value is worse
   than an error.
2. **"Pure read" covers more than the bytes.** Opening a tty, or a device
   whose driver acts on open, and reading a PCIe attribute that resumes a
   suspended device, all change system state without writing a file or
   spawning a process. Trace what each open and read *does*, not only
   what it returns. That goes for the transitive surface too (U-1).
